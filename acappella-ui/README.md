# 十四行 Sonnet

阿卡贝拉实时跟谱提示工具。戴耳机排练时，它听**整个团队**唱到哪，然后告诉你现在该唱什么音、自己唱得准不准。

名字取自 sonnet：一首小而完整的歌；「行」也是谱面上你负责的那一行。一句话版本：听见整队，唱准自己。

**核心思路**：位置由团队决定，不由自己决定。如果我跟着自己走，一旦自己节奏没跟上团队，系统就跟着一起错，那就失去了提醒的意义。

## 跑起来

```bash
npm install
npm run dev      # http://localhost:5173
npm run build    # 产出 dist/
npm run preview
```

麦克风权限要求安全上下文：**localhost 或 HTTPS** 才行，直接双击打开 `dist/index.html` 不行。

## 打包成 Android APK

用 Capacitor 8 套壳，WebView 加载打包进 `android/app/src/main/assets/public` 的 `dist`。麦克风走 Android 运行时权限：`RECORD_AUDIO` 和 `MODIFY_AUDIO_SETTINGS` 已写进 `AndroidManifest.xml`，Capacitor 的 `WebChromeClient` 会自动弹授权。

前置：JDK 17 或 21（本机 Gradle daemon 用 JDK 21），Android SDK 36。

```bash
npm install
npm run cap:sync            # 构建 dist 并同步进 android/
cd android
gradlew assembleDebug       # macOS / Linux 用 ./gradlew
```

产物在 `android/app/build/outputs/apk/debug/app-debug.apk`，装到手机：

```bash
adb install -r android/app/build/outputs/apk/debug/app-debug.apk
```

包名 `com.shisihang.sonnet`，应用名「十四行」。改完 Web 代码要重新 `npm run cap:sync` 再编译；`npm run android:open` 会尝试打开 Android Studio（本机未装则用命令行构建）。发布版需要自己配签名，Debug 包可直接安装。

Gradle wrapper 已固定到 8.13（AGP 8.13.0 的最低要求）。本机缓存里已有该发行版，首次构建不会再下载 Gradle 本体，但 Maven 依赖仍需联网。

图标与启动图在 `assets/icon-only.png` 和 `assets/splash.png`，改完执行 `npm run assets:android` 重新生成各密度资源。Android 15 对 targetSdk 35 以上默认启用预测性返回，manifest 里显式关掉了它，返回键由 `MainActivity.onBackPressed` 调 `window.__back` 处理：不在跟谱页就回跟谱，在跟谱页才退到后台。

技术栈：Vite + React 18 + Tailwind + shadcn 风格组件（本地手写，未引官方 CLI）+ OpenSheetMusicDisplay（五线谱渲染，VexFlow 内核）。没有后端，全部在浏览器里跑，音频不出本机。

## 数据流

```
麦克风 → AnalyserNode
       → YIN（单音高，只用于音量/参考）+ 多基频估计（主）
       → 谐波检验：把噪声产生的假音高筛掉
       → 各声部认领：谁的音高和谁的谱对得上
       → 冷启动定位 / 锁定跟随（两态）
       → teamBeat（团队此刻在第几拍）
       → 我该唱什么 + 我偏多少音分
       → 界面（光标、彩帘、曲线）+ 耳机提示音
```

引擎每帧吐出一个 `frame` 对象（`src/lib/engine.js` 末尾），界面层只读它。

## 曲库

谱库页目前只有 **1 首内置曲目：《欢乐颂》**（公版旋律，四声部由 `arranger.js` 生成）。

> 早期版本带 368 首（其中 345 首巴赫众赞歌占 742 KB），为了减小包体和界面复杂度全部移除。
> 想加回曲目，往 `library.js` 的 `MELODY_SONGS` 里加一条即可，格式见该文件顶部注释。
> 用户自己的谱面走「导入」和「我的谱面」，不受影响。

- 民歌、儿歌、颂歌和练习曲只用公版旋律，四声部由 `arranger.js` 生成，属于练习编配，不是原作和声。
- 曲库数据约 645 KB（gzip 约 100 KB），单独成 chunk，打开谱库时才加载，不影响跟谱首屏。
- 分类与搜索都在本地完成，没有网络请求。
- 「我的谱」：导入的 MusicXML 或文本谱保存在本机 IndexedDB，同名谱面覆盖旧记录，可随时载入或删除。数据只在本机，不上传，也不随 APK 分发。现代歌曲请走这条路，并自行确认谱面使用权。
- 曲库本身只收公版和可授权内容，不内置仍在保护期的流行歌曲。词曲版权和录音版权是两层权利，自己重新记谱或清唱也不能绕过词曲版权。

### 导入包

「我的谱」有三个批量入口：**导入**（多选 `.xml` / `.musicxml` / `.mxl`）、**文件夹**（选整个目录，自动筛出谱面文件）、**整包**（一个 JSON 一次写入几百上千首）。单文件导入会直接载入并保存；批量导入只写库，导入后跳到「我的谱」，可以搜索曲名或作曲家。

包是纯 JSON，格式见 `packs/README.md`。生成自己的包：

```bash
python scripts/build_pack.py --src <谱面目录> --work <临时目录> --out melodies.json
node scripts/build_pack.mjs --in melodies.json --out pack.json --name "我的曲目"
node scripts/check_pack.mjs pack.json
```

`build_pack.py` 认 `.mscx` 和 MusicXML，`.mscx` 会用本机 MuseScore 4 命令行先导出；只取主旋律那一个声部。`build_pack.mjs` 把旋律交给 `arranger.js` 生成四声部，所以编出的和声和应用里「配成四声部」完全同源。加 `--textures plan` 用默认织体方案，不加是全柱式；`--default-bpm` 指定原谱没有速度时的默认值。`check_pack.mjs` 检查结构、声部长度与音域。

仓库根目录的 `packs/` 放了两份现成的包：1235 首艺术歌曲，341 首公有领域流行曲。都不参与构建，也不随 APK 分发。

批量导入的实现有两处值得注意：

- `myScores.js` 的 `saveMyScores` 在一个事务里写完，并且只读一次旧记录。逐条 `saveMyScore` 会每首都全表读一遍，上千首要几十秒。
- `listMyScores` 用游标只返回摘要（曲名、拍号、速度、声部数），完整谱面在点开时才用 `getMyScore` 取。否则打开谱库要把上千首的 `parts` 全读进内存。

## 从 PDF 导入

PDF 里只有图形，没有音符数据，所以「识别 PDF」实质是 OMR（光学乐谱识别）。浏览器和手机端没有可用的 OMR 引擎，Audiveris 本身是 Java 桌面程序（GPL-3.0），不适合塞进 APK，所以识别放在应用之外做。有两条路：

**手机上直接选 PDF**：走服务器上的识别服务（`sonnet-omr.service`，Audiveris 5.11 + HTTPS），**手机不需要连电脑**，任何网络下都能用。

在「创作 → 谱库 → 导入或手写谱面 → 导入」里选一个 PDF 即可，识别完自动载入，过程中会显示排队位次。证书已打进 APK，不用手动装。

服务在 `https://101.43.109.115:443`，需要 token（已嵌进 APK），同一时刻只跑一个任务、单 IP 每小时 20 次。部署、接口、限流和排错见 `scripts/OMR-SERVER.md`。

**桌面端批量转换**：脚本直接调本机 Audiveris，适合一次转一整批。

安装 Audiveris：

1. 从 GitHub Releases 下载 `Audiveris-<版本>-windowsConsole-x86_64.msi`。
2. 不想装进系统就做管理员安装解包：`msiexec /a audiveris.msi /qn TARGETDIR=D:\Softwares\Audiveris\app`。
3. 脚本默认找 `D:\Softwares\Audiveris\app\Audiveris\Audiveris.exe`；装在别处用 `--audiveris` 传路径，或设环境变量 `AUDIVERIS`。

```bash
python scripts/pdf_to_score.py --src "D:/我的谱" --out "D:/我的谱/xml" --jobs 3
python scripts/pdf_to_score.py --src "D:/我的谱" --out "D:/我的谱/xml" --pack packs/mine.json
```

第一个命令逐份产出 `<原名>.musicxml`，拖进谱库页的「导入」即可。导入时会连同原始 XML 一起存进「我的谱」，谱面按识别结果的排版渲染。第二个命令顺带打一个包，走「整包」入口。

参数：

- `--jobs N`：同时识别几份 PDF，默认 2，最多 8。Audiveris 单份约占 1 GB 内存，开太多只会互相拖慢。
- `--bpm 84`：原谱没有速度标记时用的速度，默认 84。
- `--no-repeats`：不展开反复记号。默认展开，正反反复按 `times` 复制小节，谱面按实际演奏顺序走一遍。
- `--force`：忽略缓存重新识别。中间产物在 `<out>/.work` 下，含 Audiveris 的 `.omr`，可以随时删。

识别之后，脚本会把这些情况收拾干净：

- 整份 PDF 识别失败就按页重试，空白页、封面页跳过并报出来，不静默丢弃。
- 一行谱表上两个声部（缩编谱）按 `<voice>` 拆成两份，声部重名时自动编号，避免两个都叫 Voice。
- 和弦只留最高音，报告里给出去掉了多少个和弦内音。跟谱只需要一条线，钢琴谱也能用。
- 拍号变化和八度谱号（男高音常用的高音谱号加 8）按小节读取，音高换算成实际音高。应用内部只记一个拍号，取出现次数最多的那个；识别结果里的 MusicXML 保留每小节的拍号。
- 一小节的音超过拍号就在小节线处拆开并补连音线，不够就补休止符；首小节不满算弱起，不补。
- 连续三小节都提前结束、而且缺的拍数一样，报告里会提示「可能漏读了拍号变化」，方便回原谱确认。
- 一份 PDF 当一首曲子。多首合订的谱集先按曲拆成单份 PDF 再转。

### 识别精度

当时用 345 首众赞歌抽 5 首做测试语料（这批曲目后来从内置曲库移除了，测试记录保留作为导入能力的参考）。由 MuseScore 排版导出干净 PDF（不是扫描件），把识别结果与原始音符逐个对比：

| 曲目 | 音高 | 时值 |
|---|---|---|
| BWV 313 | 100% | 100% |
| BWV 104/6 | 98.5% | 100% |
| BWV 180/7 | 98.1% | 98.4% |
| BWV 269 | 96.4% | 96.0% |
| BWV 56/5 | 43.7% | 72.6% |

前三首只错个别音。BWV 269 丢了最后一小节的音符。BWV 56/5 在一处时值上认错，后面整段错位，数字才这么差。

干净排版的四行谱面基本可用，但导入后仍要对着原谱校一遍。扫描件、手机拍照、纸面倾斜、歌词挤进谱面的版本，精度会明显低于上表。应用里没有专门的校对界面，改音就改下方那段文本记谱，改完重新「载入」。

## 主旋律自动配多声部

谱库页底部的「导入或手写谱面」里写一条旋律，点「配成多声部」，选编制，就会生成对应声部数的合唱谱。流程是：推调性 → 每小节定和弦 → 按编制铺声部栈 → 按每小节选的织体排节奏。

支持七种编制：混声四部（SATB）、混声五部（SATTB）、混声六部（SSATTB）、混声八部（SSAATTBB）、女声四部（SSAA）、男声四部（TTBB）、女声三部（SSA）。

声部栈的算法：先按旋律音高定主旋律所在声部（TTBB 会整体移低八度，不会让男高唱到 A5），再从旋律往下逐层铺和弦音。相邻声部的最小间隔按 GAPS 递增（上密下疏），整体再按可用音区缩放——否则八部会在低音区撞成一堆同度。低音优先落在根音上；音区用尽时允许同度，但绝不塞调外音。

调性用 Krumhansl-Kessler 调性轮廓做相关性判断，再叠加三条约束：调外音扣分、末音落在主音加分、主和弦三个音要尽量齐全。小星星不会被判成 D 小调，带 F 还原的旋律也不会被拉到 G 大调。判错时可以点调性按钮在三个候选里换。

和弦在小节内按旋律音的覆盖度打分，强拍权重更高，I/IV/V 有小幅优先，首尾小节偏向主和弦。

### 织体

同一个和弦可以有完全不同的写法，这是编配里比和弦更影响听感的一层。生成器把织体做成每小节一个标记：

| 织体 | 写法 | 常用位置 |
|---|---|---|
| 独唱 | 只有主旋律 | 开场、主歌第一句 |
| 齐唱 | 四声部同度唱旋律 | 最后一遍副歌、渐强结尾 |
| 三度差 | 女低在旋律下方走调内三度，男高男低休息 | 主歌，留空间 |
| 长音 | 下三声部各唱一个和弦音铺住 | 过渡、旋律走动多的段落 |
| 柱式 | 四声部同节奏，旋律每个音配一个和弦 | 副歌，饱满规整 |
| 敲钟 | 下三声部依次晚进半拍、一拍、一拍半，主旋律准时 | 乐句起点、终止式 |
| 节奏 | 下三声部走八分音型（一下一空） | 快歌、桥段 |

界面里先用「画笔」选一种织体，再点小节涂上去；「层层加厚」给默认方案，「全柱式」一键铺满。默认方案是：第 1 小节长音铺满、第 2 小节柱式、每四小节插一个节奏型、末小节敲钟。开头不再用独唱或三度差，否则男高男低会整两小节休止，播放起来缺低音。

声部排布按编制逐层铺和弦音，约束相邻声部的高低顺序与最小间隔，并让低音尽量落在根音上。三音是和弦的性格：女低够得到就由女低唱三音，够不到时四声部改成男高唱三音、男低唱根音，避免 C 和弦写成 C-G-C-G 这种空五度。主旋律移动的幅度由最高声部的音区决定，不再固定按女高音区处理。

导入 MusicXML 时声部名会保留分部编号：Soprano 1 / Soprano 2 识别成 S1 / S2，Bass 1 / Bass 2 识别成 B1 / B2，不会再并成同一个 B。谱面渲染按声部数分级缩放：一到二部 1.25、三到四部 1.05、五到六部 0.9、七到八部 0.75，更多更低。光标停在屏宽 70% 处滚动，当前小节从左完整露出；跟谱页底部预留 150 像素放气泡和按钮，谱面不会钻到控件底下。

所有织体输出的每小节时值都等于拍号，落在十六分音符网格上，MusicXML 的 divisions 除得尽。

## 播放

跟谱页右下角麦克风左边是播放键，按谱面 BPM 把所有声部一起奏出来，光标跟着走。这是听一首歌最短的路径：载入曲目，点播放。

- 播放在**当前定位处**开始；点谱面任意位置会从那一拍接着放，谱尾再按一次从第 0 拍开始。
- 播放和跟唱互斥。按播放会停麦克风，按麦克风会先停播放，并停在你停下的那一拍，接着就能跟唱。
- 播放引擎独立于提示音：`player.js` 里的 `ScorePlayer` 有自己的 `CueEngine` 和总线限幅，换播放音色不影响跟唱提示音。音色在设置页的「播放」里选，默认「合唱 啊」，另有「合唱 哦」、管风琴、弦乐、钢琴、长笛、木琴。
- 音色是真实录音采样，来自 MuseScore 4 自带的 MS Basic 音源（MIT 许可，内含 FluidR3 采样），用 `scripts/build_samples.py` 拆成单音 OGG 放进 `src/assets/samples/`，26 种音色共 226 个采样、约 5.7 MB。一个音色按小三度存一个采样，播放时用 `playbackRate` 变调覆盖整个音域。
- 合唱采样是真的「啊」「哦」衬词录音，四声部各取自己音区附近的采样；采样是单声道，播放时按声部声像铺开。采样没加载好（或某个音高超出采样范围）时，自动退回原来的共振峰合成，第一次发声不会哑。
- 采样音色的延音靠循环采样中段：跳过起音，在 35%–85% 之间循环，长音不会变成无限拖尾的起音段。打击类（钢琴、木琴）不循环，让采样自然衰减。
- 混响是一段现场合成的噪声脉冲响应，不加载 IR 文件；四个声部按声像铺开（女高偏左、男低偏右），主旋律比内声部高约 1.6 dB，听得出旋律。
- 排期是滚动的，只提前 0.6 秒把音排进音频时间轴，所以三十秒的曲子也只有十几个 voice 在排队。
- 停止时整条播放总线 5 毫秒淡出，切歌、拖进度都不会有爆音。
- 播放前会停掉持续低音和持续参考音，避免和曲子打架；离开跟谱页会自动停止播放，持续低音也会一起停，因为别的页面没有停止入口。
- 换谱会把位置重置到第 0 拍，不会从上一首停下的地方接着播。

谱库列表每一项也有一个播放键，就地试听前四小节，不改动当前载入的谱面。换分类或换搜索词会停掉试听。

设置会存进 localStorage，下次打开仍是上次的音色、音量、定位方式和演唱传统。声部开关（参与定位的声部）跟谱面绑定，不持久化。

## 跟谱方式：点谱面定位

默认不再靠听声辨位。人在谱面上点一下，位置就定在那里，之后光标按谱面 BPM 往前走，唱的时候只做小幅校正。

理由是在线跟谱的两个难点都不在算法调参：一是多声部同时唱的基频分离本身不稳，二是乐谱里重复乐段太多（欢乐颂第 0 到 11 拍和第 16 到 27 拍几乎一样），再好的对齐器也要在几个候选里赌一个。点一下没有歧义，用户本来就知道自己在第几小节。

实现分三层：

- **定位**：`scoreGeometry` 给每个音符带上绝对拍号，`ScoreView` 据此建一张 `{x, beat}` 表；点击时按屏幕横坐标找最近的音，换算成拍交给引擎。横向拖动超过 10 像素仍算翻谱，不会误触发。
- **时钟**：`Pilot.mode = 'manual'` 时跳过整套冷启动和在线对齐，`teamBeat` 每帧按 `dt / secPerBeat` 前进，到谱尾停住。这一条路径的 CPU 消耗比自动跟谱低一个量级，因为它不做全谱搜索。
- **微调**：检测到自己的音头（音高跳变或从静音进来）时，找最近的谱面音头，把时钟往那边拉 `误差 × 0.35`，单次最多 0.25 拍；误差超过两拍认为是点错了位置，不硬拽。另外右下角麦克风按钮上方有「− / +」两个按钮，手动推半拍。

设置页的「跟随定位」可以在手动和自动之间切。自动模式保留原样，适合一个人练、且乐句不重复的曲子。

## 分轨录音转谱

录音页底部的「转成谱面」把已录的几条轨拼成一份多声部谱。这是目前唯一能可靠拿到合唱谱的路径，因为每条轨只有一个人，单声部转录在合成测试里验证到 0 音分误差。

做法在 `src/lib/takescore.js`：每条 take 的 AudioBuffer 走 `framesFromBuffer` 离线切帧，`transcribe` 转成音符，再按 `startBeat`（自动对齐的结果）和 `offsetMs`（手动微调）在开头补对应拍数的休止。同一个声部录了多条时取最新那条；没录的声部不写进谱，避免空白行。所有声部末尾补齐到同一长度，否则最后一小节会对不齐。

转谱按半拍量化，因为录音本来就对着倒计时节拍器录的。转完不清空录音，回录音页还能接着听、接着补录。

用它录侗族大歌这类传统：让歌师单独唱高音、众人单独唱低音，一次一条，出来的谱是准的。这比在混音上拆声部靠谱得多，也符合田野录音的实际做法。

## 自由记谱

哼唱页的「量化半拍 / 自由节拍」开关。量化模式按半拍吸格子，适合有拍子的旋律；自由节拍不量化，起点和时长都保留实际值，并为每个音记下**音分偏差**（`cents`），谱面仍是十二平均律，但分析结果不丢游移音高的信息。结果栏会提示有多少音偏离平均律、最大偏多少，这正是侗族大歌徵音游移、格鲁吉亚非平均律唱法需要的东西。

`hum.js` 还导出了 `framesFromBuffer(buffer)`，把一段解码后的音频按 30 帧每秒切成帧序列，跑和实时采集同一套 YIN。40 秒音频离线分析约 0.8 秒。它是「导入音频转谱」的基础，也是拿真实录音验证算法的入口。

### 真实录音上的实测

拿 Wikimedia Commons 上公有领域的格鲁吉亚复调录音（Chakrulo，1957 年国家歌舞团，PD）做了端到端测试：

- 40 秒里切出 105 个音，时长 0.05 到 1.63 秒，音分偏差在 ±50 之间均匀散开，没有统一的调音偏移。
- 帧级看，YIN 的清晰度稳定在 85% 到 99%，说明它锁得住某个周期；但音级分布是 C#、D、C、Bb、Eb、B 混在一起，说明它在三个声部之间来回跳。

结论：单麦克风加单基频估计，**分不开多声部混音**，转录出来的是一条在声部间跳跃的伪旋律。这不是自由记谱的问题——用合成旋律验证，音高误差 0 音分、26 音分的偏差原样保留、时长误差 30 毫秒以内。

### 声部跟踪的两次尝试（都只算部分成功）

为了让合唱录音也能转谱，试了两条路。界面只露出标注为「实验」的一条，另一条的实现已在整理时删除，结论保留在这里。

**一、YIN 多候选 + Viterbi**（`pitch.js` 的 `detectMulti`、`hum.js` 的 `trackLowest`）。把累积均值差分曲线上所有够深的谷都当候选，再用 Viterbi 选一条连续的音高线，每帧最多移动 7 个半音。

失败的根因很干脆：对一段三声部合成和弦（真值 C3、G2、A2、F2 各两秒），某一帧的候选只有一个值 42.8，三个基频一个都不在。时域周期对和弦取的是**共同周期**，和弦根本不存在各自独立的周期，所以候选集本身就是错的。Viterbi 再聪明也救不回来。

**二、频谱谐波求和 + Viterbi**（`fft.js` 的 `magnitudeSpectrum`）。自己实现基 2 FFT，把幅度谱转 dB 喂给 `MultiPitch.estimate`，拿到多个基频候选，再走同一套 Viterbi。这条路径在同一段合成和弦上能抓到 C3 和 A2，G2 会漏，还有八度错误。

真实录音（格鲁吉亚那段 40 秒）上的对比：

| 方法 | 音数 | 最长音 | 音级集中度 |
|---|---|---|---|
| 逐帧最强（YIN） | 105 | 1.56 秒 | 最高一级 16% |
| 频谱 + Viterbi | 81 | 3.39 秒 | D 占 27% |

频谱路径明显更像一条低音线（反复出现 D2，D 占 27%），但仍会跳声部。所以它作为「低音」模式放在哼唱页，界面写明「实验：只跟最低声部」，不承诺准确率。

## 定音

跟谱页右上角的「定音」弹出各声部起始音，取每个声部的第一个非休止音。可以点单独一行听，也可以「依次播放」（S→A→T→B，每个约 1 秒）或「一起播放」（四个音同时响 2.4 秒，用来听和弦、对音准）。用设置里选的提示音色和音量发声，不占用麦克风，跟随运行中也可以按。

## 演唱传统

设置页第一组是「演唱传统」，共 13 个档案，来自 `src/lib/traditions.js`。它不改谱面，改的是听的方式和判的标准：

- **提示方式**：以持续低音托底的传统建议开 drone，提示音式的不需要。
- **判定方式**：按音分判准 / 只看容忍带 / 只判持续音是否稳 / 只判节奏与位置。选到不判音高的传统时，跑调阈值会隐藏。
- **默认节拍器**：自由节拍的传统默认关。
- **容差**：侗族大歌这类徵音本身就游移的传统，阈值放到 60 音分，避免把风格判成错误。

按声部结构分成六类：功能和声（西方四部、Sacred Harp、isicathamiya）、持续低音（侗族大歌、格鲁吉亚、撒丁岛 tenore、阿尔巴尼亚 iso、保加利亚女声）、支声、平行音程（冰岛 tvísöngur）、泛音（蒙古潮尔、布农族 pasibutbut）、节奏互锁（印尼 kecak、因纽特 katajjaq）。

跟谱页「定音」弹层里新增「持续低音」，取最低声部的第一个音作 drone，慢起慢收，和跟谱的持续参考音分开存，互不顶掉。换谱时自动停。

这套东西的边界要说清楚：声音档案和判定策略可以适配，但记谱仍然量化到半拍，自由节拍、微分音和多人分声部都还没做。

## 三个附加功能

两个工作区（哼唱、录音）从工具栏进入时会离开跟谱界面，切换成整屏专用视图，顶部「返回跟谱」可以回去；进入时自动停止跟随，避免和麦克风抢占。工具栏在两种工作区里仍可打开，用于改设置或换谱。

**哼调记谱**（工具栏「哼唱」）
对着麦克风哼一段，停止后离线转录：中值滤波去掉毛刺，按音高跳变断句，再按 BPM 量化到半拍，最后追加成一个新声部。量化粒度固定半拍，哼的时候每个音要唱满。界面里唱的时候看实时音高，停止后下方直接显示转录出来的谱面，确认无误再「加入谱面」。加入新声部后原谱的 `_xml` 会失效，界面按内部格式重新生成 MusicXML，导入谱的原始排版信息不再保留。

**多轨录音**（工具栏「录音」）
按声部分别录，每条约 4 拍倒计时。录音与音高轨迹同步采集，停止后用整条轨迹对谱面逐拍比对，自动找回起始拍（`takes.js` 的 `alignTake`）；对不准时每轨可以 ±600 ms 微调，或点重新对齐。录音界面画的是多轨时间轴：每条轨按起始拍与录音时长落在小节标尺上，试听时有播放头，没有录音时不会显示原谱。

录音关掉浏览器 AGC，改走固定的采集链：80 Hz 高通 → 0.9 固定增益 → 软膝限幅（0.8 以下完全线性，以上平滑压到 0.96 以内）→ MediaRecorder，所以录下来的电平和监听一致，正常演唱不会被改写，唱爆也只是被平滑压住而不是削平。播放经过总线压缩限幅与 20 ms 淡入淡出，避免首尾切点和多轨叠加削顶。同声部默认只播最新一条，旧录音保留但静音，可手动打开。对齐贴合度低或覆盖度不足时不再硬给一个靠后的起点，直接按第 0 拍播放并在卡片上标注。录音卡片会显示峰值和削顶提示，峰值长期贴近 100% 时应该离麦克风远一点。

**提示音色**（设置 → 提示音色）

27 种音色，按乐器族分组，26 种是真实录音采样（MuseScore MS Basic 音源，MIT 许可），只有「正弦」是合成：

| 分组 | 音色 |
|---|---|
| 人声 | 合唱 啊 / 合唱 哦 / 独唱 啊 |
| 键盘 | 钢琴 / 大键琴 / 钢片琴 |
| 风琴 | 管风琴 / 摇滚风琴 |
| 弦乐 | 弦乐合奏 / 小提琴 / 大提琴 / 低音提琴 / 竖琴 |
| 木管 | 长笛 / 单簧管 / 双簧管 / 竖笛 |
| 铜管 | 小号 / 长号 / 大号 / 圆号 |
| 打击 | 木琴 / 颤音琴 / 木琴条 / 钟琴 / 卡林巴 |
| 合成 | 正弦 |

每个音色在下拉里标了采样覆盖的音域（如「钢琴 Eb0–Eb7」）。选中的音色覆盖不了当前谱面时会提示「超出音色音域」——采样会被拉伸超过 6 个半音，音色失真，换个音色更好。持续参考音播放中换音色会原地无缝切换；采样加载完成后，正在响的持续音也会自动换成采样。

重新生成采样包：

```bash
cd acappella-ui
python scripts/build_samples.py            # 全部 26 种音色，约 5.7 MB / 226 个采样
python scripts/build_samples.py --timbre choir   # 只重建一个音色（会合并进已有 manifest）
python scripts/build_samples.py --check    # 只列出可用的音源采样，不写文件
```

脚本直接解析 SoundFont 的 RIFF 结构（sf3 里每个采样是一段独立 Ogg Vorbis），不走 MuseScore 的命令行渲染——实测它的 `<midi-program>` 和 MusicXML `part-name` 在批量导出时都不可靠，十几种乐器会导出成同一段音频。换音源只要改 `--sf`，或在脚本的 `TIMBRES` 表里加匹配规则。

构建时踩过两个坑，脚本里都有对应处理：

- **libsndfile 的 Vorbis 编码器单次写入超过约 45 万帧就崩进程**（Windows 上是 0xC0000409）。钢琴最低几个音是 14 秒长采样，会超。`write_ogg()` 会自动把长采样降采样到能一次写完的帧数；钢琴最低音 44.1 kHz → 32 kHz，听不出差别。
- **同一个进程里连续解码多个 sf3 采样也会崩**。所以每个采样开独立子进程（`--one` 是内部入口），单进程模式留了 `--no-batch` 只用于调试。

## 撤销 / 重做

跟谱页工具行最左侧两个按钮。只管**谱面编辑**这一条线：

- 钢琴卷帘（拖拽、增删、改时值）
- 力度（整首档位、曲线自动化）
- 和弦轨套用后的编配结果
- 哼唱结果加入声部

**不包含**录音轨和设置——它们各有生命周期，混进一个历史栈会让「撤销」行为难以预测。

### 三个设计取舍

**1. 存快照而不是存操作**

谱面对象通常几 KB 到几百 KB。存快照换来的是「任何编辑都不用单独写 undo 逻辑」，加新编辑功能时不用动历史模块。存操作要写反向操作，容易漏，漏了就是数据损坏。

**2. 合并连续编辑**

拖一个音会连续触发几十次 onChange。不合并的话按一次撤销只退一个像素。实现上用 debounce：同一个 mergeKey 的编辑在 700ms 内合并成一步。

实测：钢琴卷帘连续拖 3 次，**一次撤销**就回到原状。

**3. 换谱不进历史**

打开另一首谱是「换文档」，不是「编辑」。换谱时清空历史栈——否则撤销会把用户带回上一首，很容易误操作。

上限 50 步。

## 工程管理

设置 → 工程。一个工程包含：

| 内容 | 存储 |
|---|---|
| 谱面（parts / bpm / bar / title） | IndexedDB（JSON，几 KB） |
| 和弦轨、织体轨、力度曲线 | 同上 |
| 录音轨 | IndexedDB（16-bit PCM，一分钟单声道约 5.5 MB） |
| 当前声部 | 同上 |

- **保存 / 另存为 / 打开 / 删除**，按保存时间倒序
- 打开工程会整体替换当前编辑状态，并**清空撤销栈**（换工程等于换文档）
- 只存本机，不上传

### 为什么不复用「我的谱面」

`myScores` 存的是「导入的原材料」（可能上千首，只读为主）。
工程是「我正在做的东西」，包含录音这种大块二进制，两者生命周期和体量都不同。

## 导出格式

| 格式 | 说明 |
|---|---|
| WAV | 16-bit，采样率可选 44.1 / 48 / 32 / 22.05 kHz |
| **MP3** | lamejs 纯前端编码，码率 128 / 192 / 256 / 320 kbps |
| MusicXML | partwise，含 `<velocity>` |
| MIDI | SMF format 1，每声部一 track |

采样率在**离线渲染时就按目标值跑**（`OfflineAudioContext`），不是渲完再重采样——少一次全量拷贝和一次精度损失。

### lamejs 的坑

lamejs 1.2.1 的 npm 主入口是 CommonJS，靠 `require` 串起 MPEGMode / Lame / BitStream 等十几个文件。Vite 打包时这些隐式全局依赖会丢失，运行时报 **`MPEGMode is not defined`**。

官方给浏览器用的版本是 `lame.all.js`：自包含 IIFE，末尾挂到全局。所以走静态资源加载（放 `public/lame.all.js`），不走 npm import。

### 为什么不是五个平级入口

早期是「跟谱 / 哼唱 / 录音 / 谱库 / 设置」五项平铺。问题是它们的层级并不平等：

- 「哼唱」「录音」都是把声音变成谱面，终点都是回练唱页
- 「谱库」是选一首装进来，终点也是回练唱页
- 只有「练唱」和「设置」是常驻的

平铺五项会让人以为它们是五件独立的事，实际有三个只是输入方式。收进「创作」域之后，主次一眼可见。

### 设置页为什么分子页

- 没有层级，找「跑调阈值」要滑过整个效果器
- 高频项（音色、音量）和低频项（限幅比、限幅阈值）平起平坐
- 一屏十几个滑块，看不出哪个重要

| 子页 | 直接可见 | 收进折叠区 |

| 演唱 | 演唱传统、提示音模式/音色/音量、跟随方式 | 八度、跑调阈值、下一音提前、节拍器、声部开关 |

| 界面 | 显示唱名、只显示我的声部 | — |
| 导出 | 音色、归一化、三个导出按钮 | — |

## 两态机制（最关键的设计）

```
按下开始 → cold（攒约 0.9 秒和声走向，全谱对齐一次）→ locked
                                                        ↓
                               默认接着走（跟谱器只在 pos−1 … pos+3 的小窗口里活动）
                                                        ↓
                               持续失配 2.5 秒 → 回到 cold 重新定位
```

锁定后**不再满谱搜索**。否则唱到和前面重复的和声段时，会被吸回前面的段落。要不要重新定位，只由一个监控判据决定（当前听到的和声 vs 谱面此刻）。

## 改代码前必须知道的几件事

这些是踩过的坑，改动时容易再踩回去：

1. **和弦匹配绝不能做八度归一**。否则男低的 C3 会去顶替女高的 C4，几个声部互相"代班"，不同段落的代价全被抹平，等于没匹配。八度只能作为**整体偏移**去搜索（男声团整体低八度唱是真实场景）。
2. **和弦匹配要一对一分配**，不能各算各的。一个观测音被多个期望音重复认领，是"区分度只有 0.04"的根因。
3. **OSMD 是按容器宽度决定排几行的**。它的 `Endless` 指"纵向无限高"，不是无限宽——想要单行横向卷轴，必须给超宽容器。容器加 `flex` 居中会被压回视口宽度（`shrink-0` 解决）。SVG 宽度等于容器宽度、不是谱子宽度，右侧空白要裁。
4. **跟谱用真实时间建模，不依赖帧率**。代价按 `dt` 积分，`hold` 用秒。写死帧率会导致浏览器实际帧率不同时越跟越超前。
5. **静音时必须锁住位置**。安静时谱面每个位置的匹配代价都一样，不锁就会一路滑到结尾。
6. **冷启动要能拒绝低质量定位**。噪声里随机音高也能"匹配"出一个最优起点，但那是乱指的；宁可多等，也别锁到瞎猜的位置。
7. **`jumpTo` 必须把"已唱了多久"一起带过去**。清零的话跟谱器以为这个音才刚开始，要多等整整一个音才肯往下走。
8. **首次冷启动不要搜速度**。窗口不到 1 秒，估出来的速度是瞎猜的（实测会把 1.0 估成 0.8）。速度搜索只留给窗口更长的重定位。

## 力度

力度分两级：

**整首力度**（跟谱页 → 定音 → 整首力度）：pp / p / mp / mf / f / ff 一键把当前谱面所有音设成同一档。适合先把整首歌定个基调。

**逐音力度**（文本记谱里写）：

```
S: C4 1 mf D4 1 pp E4 2 f
S: C4 mf 1 D4 pp 2          # 力度写在时值前面也可以
S: !f C4 1 D4 1 !p E4 1     # !f / !p 是行级切换，之后的音都跟着变
S: C4 1 D4 1                # 不写就是 mf（默认 0.58）
```

八档力度对应 0.16 / 0.24 / 0.34 / 0.46 / 0.58 / 0.72 / 0.84 / 0.94（ppp/pp/p/mp/mf/f/ff/fff）。

力度贯通到所有环节：

| 环节 | 效果 |
|---|---|
| 播放 | 每个音按自己的力度乘进增益，整首不再是平的 |
| 导出 WAV | 和试听完全一致（同一套换算） |
| 导出 MIDI | 写成 note-on velocity（pp→52，ff→127） |
| 导出 MusicXML | 写成 `<velocity>`，其它软件打开时也能还原 |
| 导入 MusicXML | 读 `<velocity>`，自家导出的谱能完整往返 |
| 编配 | 主旋律的力度带到下三声部，整段像一个合唱团在同一个气口上做强弱 |
| 谱面 | 彩帘条粗细跟着力度（pp 约 2.4px、ff 约 8.4px），一眼看出该轻该响 |

默认力度是 mf，和以前固定增益的听感一致——不写力度的老谱面听起来不会变。

## 效果器

设置页 →「效果器」。影响**整谱播放**和**导出 WAV**，不影响跟唱提示音。

| 参数 | 范围 | 说明 |
|---|---|---|
| 混响量 | 0–100% | 0 是干声，越大空间感越强（内部映射到干湿 0–50%） |
| 混响时长 | 0.6–4.0 秒 | 礼堂约 2 秒，教堂 4 秒以上 |
| 声像宽度 | 0–100% | 0 全部居中，100 从左到右铺满（内部映射到 ±0.35） |
| 限幅阈值 | -24–0 dB | 多声部叠加的安全阀 |
| 限幅比 | 1:1–10:1 | 超过阈值后压多少 |
| 输出增益 | 0–150% | 整体推高或衰减 |

「恢复默认」一键回到 混响 40% / 1.8 秒 / 声像铺满 / 3:1。

### 为什么单独做一个 fx.js

以前效果链在 `player.js` 和 `render.js` 里**各写了一份**（限幅 -7dB/3:1、混响 1.8s/干湿 0.2、声像 -0.35..+0.35）。改一个地方另一个就不同步，导出的听感和试听对不上。现在集中到 `src/lib/fx.js`：

```
声部各轨 → bus → ┬→ limiter → output → dest
                 └→ reverb → wet ─┘
```

- `buildFxChain(ctx, fx, dest, impulse)` 在实时和离线上下文里都能用
- `panFor()` / `partGainFor()` 统一声像和声部音量
- `makeImpulse()` 统一混响脉冲响应

### 两个连带修掉的问题

1. **导出的混响尾巴被切断**：`render.js` 原来写死 `TAIL = 2.6` 秒。混响时长调到 4 秒时，尾巴会在第 2.6 秒被硬切。现在尾长 = `0.8 + 混响时长`，渲染时长跟着变（实测混响 1.0 时输出从 21.8 秒变成 24.1 秒）。
2. **老用户的 settings 没有 fx 字段**：`FxPanel` 里 `{ ...DEFAULT_FX, ...(fx || {}) }` 兜底，不会崩。

### 实测

| 项目 | 结果 |
|---|---|
| 混响量 0 vs 0.9 | 末尾 1.5 秒的 RMS 从 **0** 变成 **0.00019**（干声完全没有混响尾） |
| 混响时长 1.0 | 输出时长 21.8 → **24.1 秒**（尾巴留够） |
| 声像宽度 0 vs 100 | 左右声道相关从 **1.000** 降到 **0.920**，且左右 RMS 不同 |
| 参数持久化 | 改动写入 `localStorage['sonnet-settings'].fx`，刷新后 slider 回显 90/80/20/50/50 |
| 导出用同一套参数 | `renderScore(sc, { fx })` 渲染正常 |

### 力度自动化

横轴小节、纵轴力度（ppp～fff 八档）。点一下加控制点，上下拖动改值，相邻控制点之间线性插值。

**手写力度优先**：文本记谱里显式写的 `mf` / `pp` 不会被曲线覆盖。实现上给这类音打 `explicitVel` 标记，`applyAutomation()` 跳过它们。

### 两个真问题

**1. 自动播种产生了「平坦的多点曲线」**

打开自动化页时会从现有谱面反推一条曲线。第一版每小节产一个点，整首力度一样时就得到 8 个全是 0.58 的点。用户点第一小节和最后一小节后，中间 6 个 0.58 的点还在，曲线变成「两端变、中间不动」——看起来像 bug，实际是数据形状不对。

修正：`extractAutomation()` 压缩——值相同的小节合并，只在值变化处留点。整首一样时只留一个点。

**2. 在 `setState` updater 里调用另一个 `setState`**

```js
// ❌ 未定义行为，React 18 严格模式会重复执行 updater
setAutomation((prev) => {
  setScore((sc) => applyAutomation(sc, points, sc.bar))
  return points
})
```

拖动控制点时这个回调连续触发，实测只有第一个点生效。改成用 `useRef` 存最新曲线：

```js
const automationRef = useRef([])
const applyAutomationToScore = useCallback((next) => {
  const points = typeof next === 'function' ? next(automationRef.current) : next
  automationRef.current = points
  setAutomation(points)
  setScore((sc) => { ... })
}, [])
```

### 一个测试陷阱（不是产品 bug）

`document.querySelector('canvas')` 命中的是 `ScoreView` 的叠加层画布（宽 1458px，因为五线谱是横向卷轴），不是自动化画布。测试脚本按它算出的坐标点击，落点全在屏幕外。

给自动化画布加了 `data-automation-canvas="1"`。同时把三个编辑器根节点都加了 `w-full min-w-0 max-w-full overflow-hidden`，防止将来被超宽父容器撑开。

### 实测

| 项目 | 结果 |
|---|---|
| `valueAt` 插值 | 0.24 → 0.54（中点）→ 0.84，超出范围取端点，空数组返回 null |
| `applyAutomation` | 4 个音跨 4 小节得到 0.24 / 0.16（显式，未覆盖）/ 0.54 / 0.69 |
| 控制点增删 | 同小节替换、删除、排序都正确 |
| `extractAutomation` 压缩 | 整首 0.58 → 只留 1 个点（原来 8 个） |
| **端到端渐弱** | 点第 1 小节 ff(86) + 第 8 小节 ppp(10) → 谱面 8 小节实际值 **0.86 / 0.75 / 0.64 / 0.53 / 0.42 / 0.31 / 0.20 / 0.10** |
| **和弦覆盖生效** | 第 1 小节设 V7 后 A 声部 60,62,60,62 → 60,59,59,59；T 55,59,55,59 → 55,55,55,55；B 48,43,48,43 → 48,50,50,50 |

## 变速不变调

跟谱页 → 定音 → 播放速度，六档：50% / 65% / 80% / 原速 / 125% / 150%。

影响整谱播放和导出 WAV；跟唱提示音不受影响（提示音本来就按目标频率生成，与速度无关）。

### 实现

本项目的「变速不变调」天然成立，因为**每个音都是按目标频率独立生成的**：

- 采样音色：`cue.js` 用 `playbackRate` 把采样变调到目标音高，与时间轴无关
- 合成音色：直接按频率合成
- 时间轴：由 `tempo.js` 的 `TempoMap` 统一换算，改 `rate` 就够了

所以不需要对整段音频做时间伸缩——那是对「已录好的成品音频」才需要的技术。

### 中途变速

谱面可以带速度表（`score.tempos = [{ beat, bpm }, ...]`），《Echo》在 1/8/64/73 小节分别标了 65/95/80/95。`TempoMap` 负责三件事：

- `secAt(beat)` / `beatAt(sec)`：拍与秒互转。拍→秒分段线性累加，秒→拍二分查段再段内反解
- `secPerBeatAt(beat)`：某一拍此刻的秒/拍，跟谱器用它估「这个音该唱多久」
- `rate`：变速播放时整条表一起缩放，段与段之间的比例不变

播放、导出、进度条、跟谱器都从这一个对象取时间，不再各自写 `60 / bpm`。没有速度表时退化成单速，行为和以前完全一致。

### 附带实现的 WSOLA

`src/lib/stretch.js` 提供 `timeStretchMono()` / `timeStretch()`，用于需要处理成品音频的场景（比如未来给录音轨变速）。

实现要点，两处都踩过坑：

**1. 分析步长公式**

```
analyzeHop = hop * rate     ✅
analyzeHop = hop / rate    ❌
```

推导：输出长度 ≈ 输入长度 / rate。输出帧数 = outLen / hop，输入覆盖长度 = 帧数 × analyzeHop。要求输入覆盖长度 ≈ 输入长度：

```
(outLen / hop) × analyzeHop ≈ n
代入 outLen = n / rate → (n / (rate·hop)) × analyzeHop ≈ n → analyzeHop ≈ rate·hop
```

写成 `hop / rate` 会让输入只推进应有的 `1/rate²`，等于又拉伸了一次。实测 f0 偏 −545 音分（rate=0.5）/ +1261 音分（rate=2）。

**2. 搜索门限必须覆盖一个基音周期**

`TOLERANCE` 一开始取帧长的 2%（≈20 采样）。100–300 Hz 人声的周期是 150–440 采样，20 采样根本找不到相位对齐点，拉伸后频谱被破坏——实测基频偏 ±250 音分。

改成帧长的一半（512 采样，可覆盖 43 Hz 以上）后，基频误差压到 **−1 ~ +4 音分**。

**3. 两级搜索控制成本**

门限放大 25 倍后计算量暴涨（2 秒音频 244ms）。改成粗搜（每 8 采样）+ 精搜（最优点 ±8 逐点），耗时降到 39ms，精度损失可忽略。

### 实测

`timeStretchMono()` 单声道：

| rate | 输出帧数 | 期望 | 基频误差（正弦） | 基频误差（合唱采样） | RMS |
|---|---|---|---|---|---|
| 0.5 | 176400 | 176400 | +1 音分 | 0 音分 | 0.354 / 0.198 |
| 0.6 | 147000 | 147000 | 0 | — | 0.354 |
| 0.75 | 117600 | 117600 | +1 | 0 | 0.354 / 0.200 |
| 1.0 | 88200 | 88200 | 0 | 0 | 0.354 / 0.200 |
| 1.25 | 70560 | 70560 | −1 | +1 | 0.354 / 0.197 |
| 1.5 | 58800 | 58800 | 0 | +1 | 0.354 / 0.197 |
| 2.0 | 44100 | 44100 | 0 | +6 | 0.354 / 0.199 |

|---|---|---|---|

### 已知限制

- WSOLA 在 <0.5 或 >2.0 时明显颗粒感，`STRETCH_LIMITS` 拦住
- 复调密集时可能选错帧，中频略糊
- 各声道独立做 WSOLA，理论上左右帧选择可能不同（实测合唱采样左右相关保持 0.9 以上）

## 波形编辑

录音页每条轨右侧的铅笔图标 → 波形编辑器（覆盖在录音页上的编辑页）。

| 操作 | 效果 |
|---|---|
| 在波形上拖动 | 框选一段时间区间（不选＝整条） |
| 只保留选区 | 剪切：删除选区外的部分，时长变短 |
| 选区静音 | 保留时长，把选区那段的 PCM 清零 |
| 淡入 / 淡出 | 在选区内做线性淡入淡出 |
| 音量 ±3dB | 增益 ×1.41 / ×0.71 |
| 归一化 | 把整条轨的峰值拉到 0.9 |

编辑结果立刻写回这条录音的 `AudioBuffer`，混音试听和「转成谱面」都用新波形。轨道卡片上会标「已编辑：剪切」这类状态。

### 为什么「静音」和「剪切」分开

多轨录音是靠 `startBeat` + `offsetMs` 对齐的。剪切会改变长度，如果剪掉的是开头，后面整条轨的时间轴就偏了。所以：

- **静音**：时长不变，安全，适合去掉一次咳嗽
- **剪切**：明确改变长度，适合去掉首尾多余的部分

### 为什么不做撤销栈

编辑是幂等的（不满意就重新录）。撤销栈要为每一步存整段 PCM——一分钟立体声 48kHz 就 11 MB，手机上放不下。所以每次操作直接生成新 buffer。

### 绘制

不画原始采样点。`waveformEnvelope()` 按画布列数抽 min/max 包络（每列保留上下沿），4000 万个采样也能一帧画完，而且能保留尖峰（只取平均会看不出削顶）。

### 实测

| 操作 | 结果 |
|---|---|
| 剪切 2.0s → [0.5, 1.5] | 时长 1.00 秒、frames 48000（精确 50%） |
| 增益 ×1.4 | 峰值 0.4998 → 0.6997（比 1.400） |
| 选区静音 | 该段 RMS **0**，段外不受影响 |
| 淡入 0–1s | RMS 0.010（0–0.05s）→ 0.141（0.5–0.6s） |
| 淡出 1–2s | 末尾 0.0004（基本归零） |
| 归一化 | 峰值恰好 **0.9** |
| 真实录音剪切 | 1.56s → **0.64s**，frames 74880 → 30903 |
| 真实录音 -3dB | 峰值 0.892 → **0.633**（0.892 × 0.71） |

## 钢琴卷帘

跟谱页顶部点「编辑」进入，是覆盖在跟谱页上的编辑页（不占底部导航位置）。

| 操作 | 效果 |
|---|---|
| 点空白格子 | 在该拍插入一个音，音高取该行，时值 1 拍 |
| 点音符 | 选中，底部出现力度条和档位按钮 |
| 拖动音符 | 改音高（纵向）和位置（横向） |
| 拖音符右边缘 | 改时值 |
| 力度条 / 档位 | 改选中音的力度 |
| 删除这个音 | 移除选中音 |
| 完成 | 关闭编辑器，谱面按新音符重新渲染 |

只编辑**当前声部**（八声部一起画在手机上没法用），换个声部胶囊再点编辑就是编辑那一个。

### 内部格式带来的两处特殊处理

内部格式是**顺序累加**的：每个音的起点等于前面所有 beats 之和，没有绝对起点。这带来两个必须处理的点：

1. **改时值**：把新时长写进去，同时把后面所有音的 `start` 平移同样的距离。否则「拖长一个音」会吃掉下一个音的时间。
2. **拖位置**：没有绝对起点，所以「把第 i 个音往后挪 d 拍」等价于把第 i-1 个音的时值加长 d。往前挪则依次缩短前面的音（缩到 0.25 拍为止）。

`fromStarts()` 负责把「每个音的目标起点」反推回 beats：`beats[i] = start[i+1] - start[i]`，最后一个音保持自己的时值。这样总时值不会莫名其妙漂移。

### 踩过的坑

- `setPointerCapture` 加在子元素上会让父容器收不到 `pointermove`，拖动中途断掉。改成拖拽期间在 `window` 上监听。
- `window` 监听器注册一次就不重绑，闭包里拿到的是**上一次渲染**的 `withS` 和 `drag`，拖完改的是旧数组。用 `useRef` 转发到最新闭包（`onPointerMoveRef` / `endDragRef`），每次渲染刷新。
- 编辑后必须 `delete score._xml`：原始 XML 是导入/生成时的快照，不丢的话界面还会用旧 XML 渲染，改了等于没改。

### 调试句柄

`window.__roll` 暴露当前拖拽状态（`drag` / `sel` / `lo` / `hi` / `rowH` / `beatW`），自动化测试用。

## 导出

设置页底部有「导出」区，三种格式，全部在本机完成，不上传：

| 格式 | 内容 | 说明 |
|---|---|---|
| **WAV** | 立体声 16-bit 44.1 kHz | 用 `OfflineAudioContext` 离线渲染，复现播放引擎的声像、总线限幅和混响。可选音色；默认导出前把峰值归一化到 -1 dB |
| **MusicXML** | 4.x partwise | 导入过的谱直接导出原始 XML（保留原排版），否则按内部格式生成 |
| **MIDI** | SMF format 1 | 每个声部一个 track，带速度、拍号、调号和 GM program 号，可在 DAW 里直接打开 |

实测性能（本机 headless Chrome）：

| 场景 | 时长 | 渲染耗时 | WAV 体积 |
|---|---|---|---|
| 欢乐颂 4 声部 | 19 秒 | 0.5 秒 | 3.7 MB |
| 小星星 8 声部 | 22.7 秒 | 6.3 秒 | 3.8 MB |

MIDI 的 track name 只用 ASCII（`S - Soprano`），中文声部名放在 instrument name 事件里——MIDI 的文本事件没有编码声明，塞 UTF-8 进去很多 DAW 会读成乱码（实测 mido 按 Latin-1 解）。

导出进度条是按预计耗时平滑推进的：`OfflineAudioContext` 渲染期间没有进度回调，长度 96 秒的谱要渲染 9 秒，不做平滑的话按钮会一直显示 0% 或 100%，看着像卡死。

## 已知限制

- 单麦克风**无法真正分离**声音。这里做的是多基频估计（不去拆波形），合唱时 F1 约 0.7，漏检靠跟谱容错吸收。
- **本征歧义**：如果两段和声逐拍完全相同（欢乐颂第 0–11 拍与第 16–27 拍就是这样，实测代价完全相等 0.0141 vs 0.0141），中途加入时无法区分是哪一段。这不是 bug，是信息不足。
- 只有自己一个人唱时，位置只能由自己决定（练习模式），这是单麦克风的物理边界。
- 蓝牙耳机有 150–300ms 延迟，用"下一音提前预告"补偿，有线耳机最好。
- 哼唱量化固定半拍，不识别调号、连音线和装饰音；节奏复杂的旋律转录后要在文本谱里手动改。
- 录音只对齐整体起始拍，不逐音拉伸时值；中途变速的录音仍会对不齐。
- 录音与哼唱结果默认只在内存里；要留存得存成工程（设置 → 工程），未保存的部分刷新页面或换谱即丢失。
- 自动对齐靠音高轨迹，纯噪声或整段休止的录音找不到可靠起点，界面会提示"位置可能不唯一"。
- 播放没有连音线、装饰音和渐强记号；力度逐音可调，渐强靠力度自动化曲线近似。合唱采样是「啊」「哦」衬词，唱不出歌词；要真正唱词需要歌声合成模型（Sinsy、DiffSinger 这一类），不在当前纯前端的范围里。谱面中途变速已经支持，但录音对齐仍按单一速度估起点。
- 采样音色的音域边界靠变调拼：超出采样范围最多的音会变调到 3 个半音以上，音色会有轻微共振峰偏移（尤其合唱的高音区）。要更准就往 `TIMBRES` 里加更密的 `step`，代价是包体变大。

## 调试句柄

浏览器控制台里可以直接看引擎内部状态（测试脚本也靠它）：

```js
__pilot.phase        // 'cold' | 'locked'
__pilot.mode         // 'manual' 点谱面定位 | 'auto' 自动跟团队
__pilot.teamBeat     // 团队此刻在第几拍
__pilot.frame        // 最近一帧（含 cents / matchCost / 各声部状态）
__pilot.aligner      // 冷启动定位器（.dur / .distinct / .maxHarm）
__pilot.followers    // 各声部跟谱器
__player.playing     // 整谱播放是否在跑
__player.beat        // 播放到第几拍
__player.count       // 本次播放已经排期的音符数
__libPlayer          // 谱库试听用的那个播放器（进过谱库页才有）
```

`ScoreView` 里 canvas 上挂了 `__dbg`（当前音符序号、曲线末端坐标），`frame.dbg` 有逐帧的音高/谐波评分。这些都是诊断用的，不影响运行。
